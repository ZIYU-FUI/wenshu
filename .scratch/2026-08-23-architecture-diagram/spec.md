# Wenshu — 技术架构图（业务视角）

> 老板 2026-08-23 拍：补一张大的技术架构图，但模块表达尽量用业务或者产品表达，技术术语老板看不懂。
> Audience: 产品/业务人员。
> 这张图描述 wenshu（文枢）app 怎么把"老板写小说"这个事拆成多个"专职团队成员"互相配合。

---

## 一句话概括

> wenshu = **老板的写作工作室**。老板坐在主桌跟"文枢（写作总管）"说话，文枢不直接干活，而是把活派给 5 个**专职专家**，每个专家有自己的工具，5 个专家做完后文枢汇总回复老板。

## 业务流（老板视角讲一件事）

老板打一句："帮我续写捕快抓贼的章节，写得有江湖气一点"

```
[1] 老板在聊天框打字
    ↓
[2] 文枢收到，分析意图：
    "这是写活。派写手去扩写。"
    ↓
[3] 文枢派 2 个专家并行：
    · 研究员 → 搜原文里捕快 + 贼的相关设定
    · 写手 → 用"江湖"模板续写新章节
    ↓
[4] 写手做完，文枢自动让质检员审：
    "捕快性格对不对？跟前面设定一致吗？"
    质检员返回 verdict: pass
    ↓
[5] 文枢总结回复老板：
    "研究员找到了 3 段相关设定，写手写了 1200 字，
     质检员检查通过。这是新章节..."
    ↓
[6] 老板在对话区底栏看到模型菜单：
    当前用的 minimax-M3
    也可以选 Anthropic-Claude / OpenAI-GPT5 等（按老板配过的 key）
```

## 关键约束（产品级）

1. **所有配置只能走设置页**：老板不能在聊天里让文枢"改系统设置"，文枢也做不到（双重保险：App 是只读编译包 + 文枢内置拒绝话术）
2. **数据全部本地**：老板的小说、记忆、对话历史都在 Mac 上，不上传任何云端
3. **老板用同一个 key**：5 个专家共用老板配置的同一个 AI 服务 key（不分别配置）
4. **单一会话**：老板始终在一个长会话里跟文枢聊天，不开多窗口
5. **进度可见**：文枢派活给专家的过程实时显示在 aiDynamic 看板区（进度看板），老板不用等
