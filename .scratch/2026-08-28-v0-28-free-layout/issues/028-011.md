# 028-011 — Drag-lost regression test suite (NEW, addresses stated issue root cause)

**Type:** test (1 commit, runs on CI + pre-commit hook)
**Blocked by:** 028-004
**Blocks:** none (this is a defensive test, not a blocker for other tickets)

## Why this ticket exists

Boss 2026-08-27 OOB: **"我们出现这个议题是因为，我们的前端框架实现拖拽，功能总是经常丢失"** (the layout discussion started because wenshu's previous frontend-framework drag implementations kept losing drag functionality).

This ticket = **the structural answer**. Every drag regression in wenshu's own code = test fails = blocks merge. Drag is no longer a fragile library boundary; it's a tested surface owned by wenshu.

## What to build

An automated test suite that exercises every drag interaction in `WorkspaceView` / `PaneRenderer` / `NativeSplitter`. Tests use SwiftUI's ViewInspector (dev-only dep, NOT a runtime dep = does not violate ADR-0008) + accessibility-based drag gesture simulation.

## Test scenarios (each = 1 test case)

1. **Splitter drag → release → re-launch** (= drag-to-resize persists across app launches)
   - Simulate drag on a NativeSplitter at known offset
   - Verify `WorkspaceStore.workspace` weights updated
   - Simulate app quit (encode to JSON) + relaunch (decode from JSON)
   - Verify weights match exactly

2. **Drag tab from pane A → pane B center** (= drag-tab-between-pane adds as tab)
   - Setup: 2 panes with separate tab sets
   - Simulate drag from A's tab strip to B's content area
   - Verify pane B's tab count increased by 1
   - Verify pane A's tab count decreased by 1
   - Verify tab ID round-trips through `WorkspaceStore.movePane`

3. **Drag tab from pane A → pane B edge (right)** (= creates new horizontal split)
   - Setup: 1 pane
   - Simulate drag onto right edge drop zone
   - Verify tree gained a new `SplitNode(orientation: .row, ...)` with the dragged tab on one side and original content on the other

4. **Drag tab back** (= drag is bidirectional)
   - Repeat scenario 2 in reverse
   - Verify final tree equals the original setup

5. **Multi-tab drag** (= drag 2+ selected tabs preserves order)
   - Setup: 1 pane with 3 tabs, second tab selected
   - Select multiple tabs
   - Drag to pane B
   - Verify all 3 arrive in original order in pane B

6. **Drag splitter → drag tab → relaunch → all persisted** (= combined drag persistence)
   - Run scenarios 1+2 in sequence, then app quit/relaunch
   - Verify both interactions persisted independently

7. **Empty pane drop** (= drag onto an empty pane → drop in center as new tab)
   - Setup: pane with 0 tabs
   - Drag a tab from another pane onto the empty area
   - Verify pane now has exactly 1 tab (= the dragged one)

## Acceptance criteria

- [ ] New file `Tests/WenshuAppTests/DragRegressionTests.swift` with 7 test cases above
- [ ] All 7 tests pass on a fresh wenshu checkout (= no drag functionality lost)
- [ ] Pre-commit hook runs the suite (= shell `Tools/wenshu-devtool/hooks/pre-commit` runs `swift test --filter DragRegressionTests`)
- [ ] CI runs the suite on every PR (= `.github/workflows/test.yml` includes this filter)
- [ ] Test suite completes in < 30 seconds (= boss 8/27 修真过的速度观感)
- [ ] **ViewInspector is the ONLY allowed test dep** (= add to a separate `Package.swift` `testTarget` so it doesn't reach `mainTarget`; ADR-0008 clarification)

## Out of scope

- Visual correctness (= snapshot tests for 028-007)
- Edit mode shortcuts (= 028-006)
- ZoneEditor drag (= 028-008)

## Why ViewInspector

SwiftUI doesn't ship with first-party drag-gesture testing. ViewInspector (700★, MIT, last commit 2026-08-15 = within §11.1 window) is the only mature SwiftUI testing framework that supports gesture simulation. Adding it to the test target = does not violate ADR-0008 (which scopes runtime view-framework dependencies, not test tooling).
