## Architecture

```swift
struct PaneRenderer: View {
    let node: LayoutNode
    let activePaneID: PaneID

    var body: some View {
        switch node {
        case .split(let split):
            splitContainer(split)
        case .pane(let pane):
            PaneContentView(pane: pane, isActive: pane.id == activePaneID)
        }
    }

    @ViewBuilder
    private func splitContainer(_ split: SplitNode) -> some View {
        if split.orientation == .horizontal {
                HStack(spacing: 0) {
                    ForEach(split.children.indices, id: \.self) { i in
                        PaneRenderer(node: split.children[i], activePaneID: activePaneID)
                            .frame(idealWidth: split.weights[i] * idealUnit, minWidth: ...)
                            .gesture(NativeSplitterDragGesture(splitID: split.id, childIndex: i, weights: Binding(
                                get: { split.weights },
                                set: { newWeights in WorkspaceStore.shared.setSplitWeights(split.id, newWeights) }
                            )))
                    }
                }
            } else { /* VStack analog */ }
    }
}
```

## Drag UX (the structural answer to "drag always gets lost")

### Drag-to-resize (splitter drag)
- `NativeSplitter` is a 4 PT-wide colored line + invisible 16 PT hit area
- `.gesture(DragGesture())` captures offset
- On `.onChanged`, compute new weights (mirror v0.27 比例算法) and call `WorkspaceStore.setSplitWeights(splitID, weights)`
- On `.onEnded`, persist to UserDefaults

### Drag-tab-between-pane (the missing piece)
- Each `PaneContentView` shows a tab strip with `.draggable(tab.id)` modifier on each tab
- Each pane content is a `.dropDestination(for: TabID.self) { tabs, location in ... }` that calls `WorkspaceStore.movePane(targetPane, tab.id, position)`
- macOS 14+ `.dropDestination` is stable (replaces the buggy `.onDrop` API from macOS 11-13)

### Why this answer is structural
- wenshu owns the drag implementation = every regression = test failure = ticket blocks
- No upstream library can change SwiftUI drag semantics under us
- Drag gestures are part of wenshu's tested surface, not a library boundary

## Risk + mitigations

- **SwiftUI `.draggable` / `.dropDestination` macOS 14+ API stability**: stable per WWDC 2023 + WWDC 2024 = low risk
- **Drag gesture conflict with `NativeSplitter`'s own gestures**: use `simultaneousGesture` not `highPriorityGesture` (= standard pattern)
- **Drop target visual feedback**: ship ghost overlay during drag (hermes `drag-session.ts` reference)
- **WorkspaceStore update loop on drag end**: throttle `setSplitWeights` to `.onChanged` only on `.onEnded`, not continuously (= avoids UserDefaults write storms)
