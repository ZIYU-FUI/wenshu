## SUGGEST

### S1 — The commit body L13-14 + the in-code comment at file L1101-1103 both misframe `.cancellationAction` as the "Apple HIG convention for independent action like export/save" — Apple's documentation says `.cancellationAction` is for cancellation actions in a **modal interface** (e.g., Cancel buttons in sheets)

The commit body L13-14 states:
> `导出 ToolbarItem placement .primaryAction -> .cancellationAction (= Apple HIG convention for independent action like export/save, rendered in its own cluster with macOS auto-separation from main toolbar items).`

And the in-code comment at file L1101-1103 states:
> `// (= Apple HIG convention for independent action like export/save, visually separated from main toolbar cluster).`

Per `developer.apple.com/documentation/swiftui/toolbaritemplacement/cancellationaction`:
> `# cancellationAction — A placement for cancellation actions in a modal interface. — Cancellation actions dismiss the modal interface without taking any action, usually by tapping or clicking a Cancel button. — In macOS and in Mac Catalyst apps, the system places cancellationAction items on the trailing edge of the sheet but places them before any confirmationAction items.`

The placement is **semantically intended for modal sheet Cancel buttons**, not for "independent action like export/save". However:

1. **The placement still works in the desired way** (produces a macOS-enforced slot boundary distinct from `.automatic`), so the **fix is functionally correct**.
2. **The mechanism that produces the visual separation** is **distinct sibling placements create slot boundaries**, which IS a documented Apple HIG behavior. So the fix correctly leverages HIG slot-boundary rules — but the **cited placement** is semantically off-purpose.
3. **The commit body's analogy** (`'你是如何把新建打开导入分离出来的, 就怎么把导出分离出去'`) is correctly answered by the **placement-distinct-slot-boundary mechanism**, but the analogy is now `'./navigation' → './cancellationAction'` instead of `'./navigation' → './primaryAction'`. The Boss OOB might have intended a different placement (e.g., `.secondaryAction` or keeping `.primaryAction` and changing the 4 toggles to a different placement to make export the distinct one).

The framing concern is **non-blocking** because:
- The visual outcome (40 PT gap, export visually separated) is empirically observed via `computer_use capture`.
- The mechanism (distinct sibling placements produce slot boundaries) is documented HIG behavior.
- The change satisfies the Boss OOB spec literally (`'导出 独立'` ✓).

Recommended (NON-BLOCKING — for a follow-up doc commit, NOT a code rewrite):

(a) **Tighten the in-code comment at file L1101-1103** to be documentation-accurate:
```
// (= Apple HIG: distinct sibling placements create macOS-enforced
// slot boundaries. .cancellationAction here produces visual separation
// from the .automatic 4-toggle group, even though .cancellationAction
// is semantically intended for modal sheets — the slot-boundary
// behavior is what we want, not the modal-sheet semantics).
```

(b) **Tighten the commit body L13-14** to mention the empirical observation + the actual HIG mechanism rather than overstating `.cancellationAction` semantics:
```
- 导出 ToolbarItem placement .primaryAction -> .cancellationAction
  (= Apple HIG: distinct sibling placements create slot boundaries;
  .cancellationAction + .automatic produce macOS-enforced visual
  separation. computer_use capture confirmed ~40 PT gap between
  export and 4 toggles, satisfying Boss 18th OOB '导出 独立').
```

(c) **Consider whether a different placement would be more semantically appropriate**. Apple's HIG documentation for `.primaryAction` says: "A placement for the primary action." Export *is* arguably the primary action of the document toolbar (alongside new/open/import, but those are navigation actions). The v0.24 series has already moved the 4 toggles away from `.primaryAction` to `.automatic` (015.031), so the export was left as the sole `.primaryAction` and now has been moved to `.cancellationAction`. A more semantically accurate placement might be:
- Keep `.primaryAction` for export (semantically correct: it IS the primary action).
- Move the 4 toggles to a different placement that creates the slot boundary (e.g., `.principal` for a centered group? No — that's reserved for title widgets).

The current solution (.cancelAction for export) produces the desired visual separation but uses a semantically off-purpose value. A future ticket might explore whether `.secondaryAction` for export would be more semantically appropriate while still producing the slot boundary.

Non-blocking — the current fix is functional and satisfies the Boss OOB literally. The SUGGEST is documentation accuracy + semantic-placement accuracy, both non-breaking.

Non-blocking — the current framing is intuitive and the Boss OOB is satisfied, but the underlying mechanism is "distinct sibling placements" not "left cluster position".
