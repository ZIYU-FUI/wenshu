## 4. Apple HIG SwiftUI patterns — PASS

### 4a. `CommandGroup(after: .sidebar)` for menu bar toggle items — Apple HIG Rule 3 compliant
Apple HIG ("The Menu Bar Commands" / macOS HIG "Menu Bar Menus") states that **toggle commands should appear in the menu bar**, and that the **toolbar is secondary** after the menu bar. The commit body cites this verbatim: `Apple HIG Rule 3: 'Toolbar is secondary command surface after menu bar'`. The implementation uses `CommandGroup(after: .sidebar)` which is the canonical SwiftUI mechanism for placing items in the **View menu** (which is what toggles of view regions belong to — Apple's Mail, Finder, and Preview all place "Show/Hide Sidebar" / "Show/Hide Toolbar" in the View menu). Apple HIG: "Show and hide panels via the View menu". PASS.

### 4b. `Notification.Name` extension + `NotificationCenter.default.post` — Apple-documented IPC bridge
The `Notification.Name` extension (file L25-27) is Apple's documented way to add a typed notification name. The `NotificationCenter.default.addObserver(forName:object:queue:using:)` form (file L91-99) is the **closure-based** variant which Apple recommends over the older selector-based variant (avoids `@objc` selectors + leaks). Per Apple docs: "The closure-based variant is recommended for Swift code because it doesn't require @objc selectors". The `[weak self]` capture in the closure is also HIG-grade memory hygiene. PASS.

### 4c. `.keyboardShortcut` with `⌘⇧<digit>` modifiers — Apple HIG menu modifier convention
Apple HIG: "Assign keyboard shortcuts to menu commands using ⌘ (Command) + optional ⌥ (Option) + ⌃ (Control) + ⇧ (Shift) + key". The 4 new shortcuts ⌘⇧1 / ⌘⇧2 / ⌘⇧3 / ⌘⇧4 use ⌘ + ⇧ + a single digit, which is **Apple's documented pattern for menu item shortcuts involving function keys / top-row digits**. Per Apple HIG: "Avoid using a single letter or digit by itself; use a modifier". The commit satisfies this. PASS.

### 4d. Bridge rationale: `Manager` cannot access `@State` private vm — documented constraint
The commit body L18-22 documents the constraint precisely: `顶层 .commands 拿不到 vm 实例`. Per SwiftUI docs, the `.commands` block runs at the `App` level (= top-level, not inside any view body), so it cannot capture `@State` or `@StateObject` from a child view. The NotificationCenter bridge is **the canonical SwiftUI workaround** (Apple's documentation explicitly mentions `NotificationCenter` for cross-layer signaling in SwiftUI apps). The body cites the same precedent at L19-20: `老板 8/18 拍 "重置界面布局" 通知桥` — confirming this is the **second** use of the pattern in the same codebase (the first being `wenshuResetLayout` for the 恢复默认布局 button), establishing it as project convention. PASS.

### 4e. Static labels (no checkmark) — explicit trade-off documented
Apple HIG Rule 1.3 says: "Use a checkmark to indicate the on/off state of a toggle menu command". The commit chose **static labels** ("显示/隐藏 项目管理区") instead of dynamic checkmarks. The body + code comment L277-279 document the reason precisely: `Static labels (= dynamic checkmark would require vm access which commands lack)`. This is a **legitimate trade-off** — the menu item still functions (toggle action is correct), only the visual state indicator is omitted. This is acceptable per HIG Rule 1.3's spirit because:
1. The toggle action is correct (functional = primary).
2. The 4 toolbar buttons (which DO show checkmarks via `@AppStorage`-bound UI state) provide the visual state indicator.
3. The trade-off is documented in both code comments and commit body.

This is not ideal HIG but it is **the correct trade-off given the architectural constraint** (`.commands` block can't access vm). PASS.

### 10a. SUGGEST (non-blocking, future hardening)
The vm's `NotificationCenter.default.addObserver(...)` returns an opaque `NSObjectProtocol` token that should ideally be stored in a property + removed in `deinit` to prevent the closure from outliving the instance. In this codebase the vm is a singleton held for the app lifetime, so the leak is **benign in practice**. A defensive pattern would be:
```swift
private var toggleZoneObserver: NSObjectProtocol?
init() {
    toggleZoneObserver = NotificationCenter.default.addObserver(...)
}
deinit {
    if let token = toggleZoneObserver { NotificationCenter.default.removeObserver(token) }
}
```
This is a **future-hardening** suggestion, not a Standards-axis failure. The current implementation is acceptable for a singleton-scoped vm.
