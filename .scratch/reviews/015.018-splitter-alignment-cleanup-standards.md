## SUGGEST

### S1 — `areRightSplittersAligned` predicate's name under-describes its current role

The predicate at `LayoutShellViewModel.swift:160-163` is named `areRightSplittersAligned()`. After this commit, the predicate's callers do two distinct things based on its result:
- `App.swift:1017` `if vm.areRightSplittersAligned() { Rectangle()...position(x: rightX, y: ...).allowsHitTesting(false) }` — render the overlay (visual only).
- `App.swift:1100` `if !vm.areRightSplittersAligned() { VSplitter(...) }` — render the splitter (interactive control).

The two callers have opposing polarities (one wants true → show overlay, one wants false → show splitter), and both are inside SwiftUI `body`. The name "aligned" does hint at the polarity direction, but a clearer name would describe the **purpose** rather than the **state**: e.g. `shouldMergeRightSplitters() -> Bool` (= if true, hide D_v3 and overlay at D_v5 X = merge them into one visual line; if false, render them as independent per-band splitters). This would also make the `(a)+(b) two-part strategy` self-documenting at every call site: `if vm.shouldMergeRightSplitters() { /* (a) overlay */ }` and `if !vm.shouldMergeRightSplitters() { /* (b) hide D_v3 → render D_v3 normally */ }`.

This is non-blocking polish (the existing name is functional and the doc-comment explains the predicate fully). Carry into next refactor commit if/when a broader `LayoutShellViewModel` rename happens.

### S2 — The D_v3 conditional render adds a `View` graph identity discontinuity that costs a SwiftUI diff per drag

`App.swift:1100-1102` introduces:
```swift
if !vm.areRightSplittersAligned() {
    VSplitter(length: bandH, totalWidth: totalW, splitterIndex: 2, vm: vm)
}
```

When the user starts dragging D_v3 (= `vm.adjust(2, delta:..., totalWidth:...)` flips `toolsWRatio`), `areRightSplittersAligned()` flips from true → false on the next SwiftUI diff pass, and SwiftUI inserts the `VSplitter(splitterIndex: 2)` into the `HStack` mid-render. SwiftUI handles this correctly (no crash, no layout glitch), but it does cost one extra view-graph-identity churn per drag start (= a minor cost). The cleaner pattern would be to always render `VSplitter(splitterIndex: 2)` and apply `.opacity(vm.areRightSplittersAligned() ? 0 : 1)` (= keeps the view-graph identity stable, only changes the visual). However, `.opacity(0)` would still consume hit-testing area (= the hidden D_v3 would block the overlay line's hit testing, which `allowsHitTesting(false)` on the overlay does NOT save us from, since the overlay is *under* D_v3 in z-order). So conditional render is actually the correct choice here (= remove the view entirely so it doesn't intercept the overlay's lack of hit-testing). The current implementation is correct; flag this as an "investigated and intentionally-chosen" design point.

### S3 — `~0.2 PT at 1920 PT width` tolerance comment could explicitly cite the boss spec's "1 PT" claim

The predicate tolerance at `LayoutShellViewModel.swift:161` is `0.0001` (= ~0.2 PT at 1920 PT width). The boss spec says '一个像素不差' (= pixel-perfect, ≤ 1 PT tolerance). 0.2 PT is well within 1 PT, so this is fine. But the comment doesn't tie the number back to the boss spec criterion — a future maintainer might wonder why the tolerance is 0.2 PT and not 0.5 PT or 1.0 PT. Recommend one-line addition:
```swift
let tolerance: Double = 0.0001  // ~0.2 PT at 1920 PT width (well within boss spec '一个像素不差' = ≤ 1 PT)
```
Non-blocking polish.

### S4 — `rightX` local name could be `d_v5X` to mirror `D_v3`/`D_v5` notation in the doc-comment

The local `rightX` at `App.swift:1025` is bound to `D_v5 X` (= the visual right edge). The doc-comment at L1018-1024 uses both `D_v5 X` and `D_v3 X` notation to explain the math. A name like `dV5X` (mirroring the `d_v1`/`d_v2`/... naming elsewhere in the file, e.g. `D_v1`/`D_v2`/`D_v3` comments at L1001, L1084, L1088, L1092) would tie the local name to the boss-sketch's D_v5 designator and make the comment-local-name correspondence obvious. Non-blocking polish.
