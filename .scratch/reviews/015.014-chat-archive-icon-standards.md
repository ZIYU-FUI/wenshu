### F2 — `nonisolated(unsafe)` on `sessionId` is a Swift 6 concurrency smell that bypasses the actor-safety check instead of solving it

`ChatView.swift:92` introduces `nonisolated(unsafe) private var sessionId: String`. The commit body's justification: *"Swift 6 main-actor safe + avoids race between view + thread"*.

Three concrete problems:

1. **`nonisolated(unsafe)` is a documented unsafe escape hatch — and `sessionId` meets both conditions for it being wrong here**:
   - (a) `ChatViewModel` is `public final class ChatViewModel` (not `@MainActor`-annotated, not an actor). Calling its methods from arbitrary non-main contexts is the current pattern (see `WenshuConductor.handle(...)` -> `vm.send()` chain in `ChatView.swift:140-225`, which is `public func send() async` with no `@MainActor` isolation on `ChatViewModel` itself). So `sessionId = "..."` mutations are already crossing contexts.
   - (b) The new `public var sessionIdPublic: String { sessionId }` getter at L93 is read from the view layer (`App.swift:1534 archiveAndStartNewSession`, `ChatView.swift:312 vm.valueForSessionId()`), which is `@MainActor` (SwiftUI View bodies). The getter crosses contexts on every read.
   - (c) A Swift-6-clean fix would be either `@MainActor` annotation on the whole class, or a thread-safe accessor pattern (`@unchecked Sendable` + DispatchQueue, or `actor ChatViewModel`). Using `nonisolated(unsafe)` instead papers over the problem and silently accepts a data race.
   This is the same shape of concurrency-smell that the prior 015.014 codebase explicitly avoided for static singletons (`App.swift:855 nonisolated(unsafe) static var openSettings: OpenSettingsAction?`, `App.swift:864 static nonisolated(unsafe) var sharedConductor: WenshuConductor?`, `App.swift:866 static nonisolated(unsafe) var sharedChatStoreRef: ChatSessionStore?`, `ProviderKeychain.swift:153 public nonisolated(unsafe) static var backend: any ProviderKeychainStoring = AppleKeychainStore()`) — but those uses are static (= single allocation, intentional single sink), while this one is an *instance* property of a class that is allocated once per chat zone and is mutated via `startNewSession()` and read via `sessionIdPublic`. It is not the same pattern.

2. **The comment at L92 claims the safety basis is wrong** — `// v0.24 boss验收fix (Boss 8/25 OOB ticket 015.014): mutable so archive flow can replace. nonisolated(unsafe) for Swift 6 concurrency.` The "Swift 6 concurrency" justification is a smell-flag: `nonisolated(unsafe)` *opts out* of Swift 6 concurrency; it does not satisfy it. The Swift 6 idiom for "this property is mutated across contexts and I take responsibility" is `@MainActor var sessionId` or `actor`-isolation, not `nonisolated(unsafe)`. The current pattern signals "all callers must serialize externally" — but there is no surrounding serialization in `archiveAndStartNewSession()` (App.swift:1533-1543 — runs synchronously in the @MainActor view body, fine here) nor in `startNewSession()` (ChatView.swift:233-243 — runs synchronously too, fine here). The smell is latent: the next maintainer who calls `startNewSession()` from a `Task.detached` block will silently introduce a torn-write race.

3. **`sessionId` mutation lacks a clean interlock with the persistent store** — the issue file's per-ticket spec step 5 (`Persist vm.sessionId to chat_messages writes (= new session).`) is implemented only implicitly via the `sessionId` field change. `ChatSessionStore.append(_:sessionId:)` (referenced at `ChatView.swift:154, 201, 208`) reads `vm.sessionId` at each call site — there is no `@AppStorage`-style persistence of the new sessionId, no notification, no `oldSessionId` retained outside the local function scope. After `archiveAndStartNewSession()` returns, the only record of the new sessionId is the in-memory `vm.sessionId` field. If the user closes and reopens the chat zone before the first send in the new session, the new `sessionId` is lost and the next `init()` falls back to the default `"default"` (L95). The commit's in-memory scope is documented at `App.swift:1530-1531` as a deferred concern for ticket 015.015 — but the `nonisolated(unsafe)` choice is independent of the persistence concern and is a separate smell flag.

**Recommended fix shape**: replace `nonisolated(unsafe) private var sessionId: String` at L92 with `@MainActor private var sessionId: String` and add `@MainActor` to `startNewSession()` (matching the view body isolation). Then `archiveAndStartNewSession()` at App.swift:1533 (already in view body) needs no change. Alternative: keep `nonisolated(unsafe)` but document the external-serialization contract in a multi-line comment ("must only be called from view body which is @MainActor") — but that adds nothing over the proper `@MainActor` fix.

## SUGGEST

### S1 — `valueForSessionId()` already exists at `ChatView.swift:252` and is semantically redundant with the new `sessionIdPublic` accessor

`ChatView.swift:252 public nonisolated func valueForSessionId() -> String { sessionId }` already returns `sessionId`. The new `public var sessionIdPublic: String { sessionId }` at L93 is the same getter, with a different name. Two read-only accessors for the same field is a code smell — `ChatViewModel` already had a back-door (`valueForSessionId`) precisely because `sessionId` was `let`. Now that it's `var`, the back door duplicates the "public field reading" pattern. Recommend: drop one of the two (most likely drop `sessionIdPublic` and have callers go through `valueForSessionId()` for consistency with `valueForStore()` at L251).

### S2 — `.alert("归档当前会话?", ...)` message string ends with `。` (full-width period) but other Chinese strings in the same file use half-width `,`

`App.swift:1594 Text("当前会话和上下文将归档保存, 然后开启全新会话。")` mixes half-width comma `,` (after `保存`) with full-width period `。` (after `全新会话`). Other Chinese strings in the same View hierarchy:
- `App.swift:1760 .help("归档当前会话")` — no punctuation.
- `App.swift:1602 Text("No provider keys configured")` — English.
- `App.swift:1630 ... "无模型可用"` — no punctuation.
- `App.swift:1579 ChatZoneStubView(title: "搜索", icon: "magnifyingglass")` — half-width comma.
The Chinese-language Chinese strings in this codebase consistently use half-width punctuation (`,`) per the project's "code-point-of-truth" pattern (verified by spot-check of pre-existing strings). Mixing `。` and `,` in one sentence is inconsistent. Recommend replacing `。` with `.` (half-width period) to match the rest of the codebase.

### S3 — `prefix(12)` on UUID without defensive bounds check produces 13-char session slugs, not the documented "12 PT"

`ChatView.swift:238 let newId = "s_" + UUID().uuidString.prefix(12).lowercased()` produces a string of length 13 (`"s_"` + 12 hex chars). The commit body calls this "(= 12 PT)" verbatim, but the actual emitted sessionId is 13 chars. The `PT` notation is ambiguous here (could mean "points" or "一蒲陶" or "post-trait" — none of which actually fit). Either the comment is a typo for "12 chars" (recommend: rewrite as `(= 12 hex chars)`), or the prefix length was meant to be 12 chars including the `s_` prefix (then code should be `UUID().uuidString.prefix(11).lowercased()` — odd choice). Either way the comment is misleading.

### S4 — `archiveAndStartNewSession()` reads `vm.sessionIdPublic` twice and could combine into one let-binding for atomicity

`App.swift:1534-1542`:
```swift
let oldSessionId = vm.sessionIdPublic
let messageCount = vm.messages.count
let contextUsedBefore = vm.contextUsed
NSLog("[wenshu.chat] archive session: id=%@ messages=%d contextUsed=%d", oldSessionId, messageCount, contextUsedBefore)
vm.startNewSession()
NSLog("[wenshu.chat] new session started: id=%@ messages=%d contextUsed=%d", vm.sessionIdPublic, vm.messages.count, vm.contextUsed)
```
