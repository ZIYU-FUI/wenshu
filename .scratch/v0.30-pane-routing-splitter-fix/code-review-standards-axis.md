3. **Spec/code type drift on `useNSSplitView`** (`.scratch/v0.30-pane-routing-splitter-fix/issues/04-feature-flag-wire.md:15, 23, 25, 26, 40` vs `Sources/WenshuApp/State/WorkspaceState.swift:803`). The types differ (`Bool` vs `Bool?`) and the defaults differ (`false` vs `nil`). Functionally equivalent at the consumer (`store.workspace.useNSSplitView ?? false` at WorkspaceView.swift:123 collapses the optional), but spec drift = maintenance hazard. Soft suggestion: update issue 04 to say `useNSSplitView: Bool? = nil` (= decode-old-JSON-as-nil pattern documented in the WorkspaceState.swift doc-comment).

4. **Spec mentions a file that doesn't exist** (`.scratch/v0.30-pane-routing-splitter-fix/spec.md:253`): `added: Sources/WenshuApp/Views/Layout/PaneSplitBridge.swift`. `PaneSplitBridge.swift` was NOT added in any of the 6 commits (= `ls Sources/WenshuApp/Views/Layout/` shows no PaneSplitBridge.swift). The spec was written ahead of the implementation and the file landed as `PaneSplitHost.swift` instead (= the wrapper name evolved). Soft suggestion: update spec.md L253 to read `added: Sources/WenshuApp/Views/Layout/PaneSplitHost.swift` (= actual file name) OR document why a bridge file was planned but never created.

5. **`PaneLayout` protocol uses `@MainActor` on the method but not on the protocol declaration itself** (`Sources/WenshuApp/Views/Layout/PaneLayout.swift:34-63`). The method is annotated `@MainActor` at L56 but the protocol declaration at L34 has no `@MainActor` (= callers might call from non-main contexts and Swift 6 strict concurrency will complain). Fowler smell = **"Speculative Generality"** combined with **"Feature Envy"**: the protocol is small enough that the `@MainActor` could live on the protocol (= simpler call sites), and it's only relevant because `NSSplitViewController` is main-actor-isolated (= the constraint is AppKit's, not the protocol's). Soft suggestion: hoist `@MainActor` to `protocol PaneLayout` (= whole protocol main-isolated; matches `PaneNSController: NSSplitViewController`'s `@MainActor` class annotation at PaneNSController.swift:40-41).

6. **`PaneNSController.buildLayout()` silently mutates inherited children** (`Sources/WenshuApp/Views/Layout/PaneNSController.swift:80-84`): the `for child in children { removeChild(at: 0) }` loop removes children one-at-a-time from index 0 (because removal shifts subsequent indices). This is correct but smells of **"Mutable State"** (= the inherited children list is mutated without documentation that the controller is single-use). The comment on line 81-82 says "Reset any inherited children (= safety against reuse)" — but `NSSplitViewController` doesn't have a reuse pool, so the safety is theoretical. Soft suggestion: drop the loop OR add `@available(*, unavailable, message: "PaneNSController is single-use; do not re-init")` to a guard.

7. **`PaneNSController.installSplit`'s `parentOrientation` parameter is required but only ever takes 1 of 2 values that could be derived** (`Sources/WenshuApp/Views/Layout/PaneNSController.swift:99-120`). The caller at line 137 already knows the parent's axis (via `controller.splitView.isVertical ? .row : .column`) — passing it as a separate parameter is **"Feature Envy"** (= the caller has the data, the callee needs it; should be derived). Soft suggestion: drop the `parentOrientation` parameter and derive it inside `installSplit` from `parent.splitView.isVertical`.

8. **`PaneNSController.autosaveKey(for:)` returns `String` for `splitID: String` but the SplitNode.id is likely UUID-shaped** (`Sources/WenshuApp/Views/Layout/PaneNSController.swift:230-232`). Without verifying `SplitNode.id` type, the resulting autosaveName key `wenshu.split.FCPLayout.<splitID>` could collide if any split lacks an id (= UUID collision risk per workspace.json persistence). Soft suggestion: when you actually flip the flag ON (= PR 5), verify `SplitNode.id` is non-empty in `autosaveKey` (= fallback to a hash of the orientation+children count if empty).

9. **`PaneSplitHost.updateNSViewController` empty body is correctly protocol-mandated but worth documenting** (`Sources/WenshuApp/Views/Layout/PaneSplitHost.swift:82-96`). The body is required (NSViewControllerRepresentable contract) but the long comment explaining "Ticket 03 will: ..." is future-framework speculation (= will be stale after PR 5 lands). Soft suggestion: shorten the comment to 2-3 lines ("No-op: content is static at make-time; tree changes trigger SwiftUI re-make (= ticket 03 deferred)").

10. **`WorkspaceStore.init` UserDefaults read comment is over-documented** (`Sources/WenshuApp/State/WorkspaceStore.swift:113-123, 149-157`). The 11-line pre-block comment + 8-line inline-block comment for a 3-line `if let useNSSplit = userDefaults.object(...) as? Bool { self.workspace.useNSSplitView = useNSSplit }` is **"Long Method"** smell (= comments explaining WHY a 3-line read goes AFTER self.presets init). 11. **`useNSSplitView` field lacks a dedicated @AppStorage wrapper** (`Sources/WenshuApp/State/WorkspaceState.swift:803`). The spec uses `UserDefaults.object(forKey: "wenshu.useNSSplitView") as? Bool` in WorkspaceStore.init:155 instead of `@AppStorage("wenshu.useNSSplitView")` (= Apple's canonical SwiftUI UserDefaults wrapper). The reason given in commit `f380a2cd4` body is "WorkspaceState is Codable" (= the field needs to round-trip through JSON persistence), so `@AppStorage` can't directly back it. This is a legitimate tradeoff but the bridge at `WorkspaceStore.init:155` is **"Schemas on the Wrong Side"** (Fowler smell): the JSON model carries the flag, the UserDefaults flag carries the opt-in, and a manual `if let` keeps them in sync. Soft suggestion: add a comment to the field explaining the dual-store rationale (= "Codable JSON round-trips the flag for state export; UserDefaults is the opt-in bootstrap so users can flip the flag without rebuilding the app").

12. **`PaneNSController.makeSplitItems` renders only the FIRST tab of each pane, not the active tab** (`Sources/WenshuApp/Views/Layout/PaneNSController.swift:154-181`). Line 163-164: `guard let firstTabID = pane.tabIDs.first`. The `pane.tabIDs` list order may not match `tab.kind` selection (i.e. the user's active tab might not be `first`). When the flag flips ON, the user could see the wrong content per pane (= the first tab, not the selected tab). Soft suggestion: use `pane.activeTabID` (= should exist on PaneNode schema; verify) instead of `pane.tabIDs.first`. This is also a soft "**Wrong Default**" smell.

13. **All 6 commit messages use Chinese subject-style em-dash `—`** (`bd565247c`, `59bc66d69`, `74c327db9`, `f380a2cd4`, `210d042ba`, `d54451539`). AGENTS.md §5 forbids "no CJK punctuation" — em-dash `—` (U+2014) is technically a Latin-1 general-punctuation char, not CJK punctuation, so it survives `grep -c '[一-龥]'`. However the project convention (per recent commits: `adcab7c1b fix(wenshu): v0.30 — preview sort button...`) uses the same em-dash pattern, so it's consistent. Not a violation — flagging for context that this convention is project-wide.
