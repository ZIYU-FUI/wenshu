# v0.32 Tier-2 Apple-API-First Sweep Specification

Status: deferred specification; no source changes in this document.
Scope: high-impact, user-visible replacements after the Tier-1 chrome deletion.
Repository: wenshu.

## 1. Purpose and guardrails

This document turns the v0.32 audit into reviewable Tier-2 tickets.
Tier-2 means the change can alter visible chrome, layout, selection, or input.
The goal is to replace bespoke rendering with Apple framework behavior.
This is a specification, not an authorization to edit Swift source.

Hard rules:

- English-only documentation and commit messages.
- Create no dependency and modify no source file during specification work.
- Preserve the six-zone PaneTabBar contract and its parent-owned styling.
- Do not add Liquid Glass where Apple does not provide it by default.
- Use Apple colors, materials, and semantic controls instead of literals.
- Ship one ticket per commit after review and before the next ticket.
- Capture a before/after macOS screenshot for every visible change.

## 2. Apple-API-first check

Candidate: custom chrome background or shadow.
Replacement: native toolbar, safe-area inset, window container background,
or the system material already supplied by the containing surface.
Decision: prefer the native surface; do not paint a second chrome layer.

Candidate: custom tab and status layout.
Replacement: SwiftUI toolbar, ToolbarItemGroup, and safeAreaInset(edge:).
Decision: keep PaneTabBar only where zone-specific behavior is required;
remove wrappers that duplicate NSToolbar or safe-area composition.

Candidate: custom selected-region fill or border.
Replacement: native selection semantics, containerBackground(for:), and
Apple hierarchical ShapeStyle values.
Decision: use the semantic selection surface and avoid hand-painted strokes.

Candidate: custom hover wash.
Replacement: hoverEffect(.highlight) or the native Button style.
Decision: let the system provide hover, pressed, and keyboard focus states.

Candidate: custom divider or divider opacity ladder.
Replacement: Divider() or NSSplitView's .thin divider style.
Decision: accept Apple's one-pixel separator; do not chase visibility with tint.

Candidate: hardcoded spacing in shared chrome.
Replacement: DesignTokens values backed by one parent component contract.
Decision: migrate sites by surface, not by arbitrary global replacement.

## 3. Ticket inventory

### T2-01: Pane chrome composition

Targets: PaneStatusBar.swift, PaneTabBar.swift, and callers in the zone
chrome composition. Replace NSView layout wrappers where ToolbarItemGroup or
safeAreaInset expresses the same surface. Keep functional callbacks and
selection state. Parent PaneTabBar owns spacing, padding, background, and
separator; child icon tabs own only action and state.

Apple API: toolbar, ToolbarItemGroup, safeAreaInset(edge:), toolbarRole.
Risk: medium. Effort: medium. Impact: visible chrome and keyboard behavior.
Acceptance: six zones retain identical actions and selected states; no
custom NSView layout remains for behavior Apple already supplies.

### T2-02: Zone chrome orchestration

Target: ZonePerRegionChrome.swift. Split the monolith at Apple surface
boundaries: toolbar content, safe-area status content, and content background.
Do not create a new coordinator. Reuse the existing PaneTabBar contract.

Apple API: toolbar, ToolbarItem, safeAreaInset(edge:), containerBackground.
Risk: medium. Effort: medium. Impact: fewer conflicting layout authorities.
Acceptance: each zone has one source of truth for top and bottom chrome;
window resizing and toolbar customization remain stable.

### T2-03: Content surface materials

Targets: RegionContentBackground.swift and region callers. Remove custom
NSView or VisualEffectView behavior when Material or containerBackground
fully covers the use case. Use canonical Apple NSColor fills where a solid
pane fill is required; do not apply glassEffect per pane by default.

Apple API: Material, containerBackground(for: .window), Color(nsColor:).
Risk: medium. Effort: low. Impact: pane readability and visual hierarchy.
Acceptance: no desktop wallpaper leaks through a content pane; screenshot
proves the pane remains readable in light and dark appearances.

### T2-04: Selection and hover surfaces

Targets: RegionSelectionBackground.swift and RegionHoverWash.swift. Replace
manual border, tint, timing, and cursor bookkeeping with native selection and
hover semantics. Preserve accessibility labels and focus order.

Apple API: hoverEffect(.highlight), Button styles, selection ShapeStyle,
contentShape only where the semantic control needs it.
Risk: medium. Effort: medium. Impact: pointer, keyboard, and focus feedback.
Acceptance: hover, pressed, selected, and keyboard focus states are distinct
without custom opacity timers or duplicated overlays.

### T2-05: Divider and shadow cleanup

Targets: custom chrome shadows, divider painting, and opacity bridges found
by the audit. Replace ornamental shadows with the shadow/material behavior
of the native surface. Replace custom divider views with Divider or NSSplitView
.dividerStyle(.thin). Do not increase contrast by inventing a divider color.

Apple API: Divider, NSSplitView.DividerStyle.thin, native toolbar material,
shadow only when the Apple container uses one.
Risk: low to medium. Effort: low. Impact: consistent chrome separation.
Acceptance: no duplicate line or shadow appears in before/after comparison;
separator remains one visual hairline at normal scale.

### T2-06: Shared spacing token migration

Targets: hardcoded spacing and padding in PaneTabBar, PaneStatusBar, and
ZonePerRegionChrome. Map each value to DesignTokens only when it expresses a
shared chrome rule. Preserve intentionally local content spacing.

Apple API: parent-owned layout plus DesignTokens; no new spacing framework.
Risk: low. Effort: medium. Impact: symmetric, maintainable chrome geometry.
Acceptance: leading and trailing chrome insets match; child components accept
no padding, spacing, or background override.

### T2-07: Button and form surface audit

Targets: custom button wrappers and form-like chrome identified by the grep.
Use Button roles/styles and Form with .formStyle(.grouped) where semantics
match. Do not convert domain-specific controls merely to reduce line count.

Apple API: Button(role:), buttonStyle, Form, formStyle(.grouped).
Risk: medium. Effort: low. Impact: native focus, keyboard, and accessibility.
Acceptance: primary, destructive, and secondary actions announce correct
roles and retain existing enabled/disabled behavior.

## 4. Execution and verification

Before each ticket, run the candidate grep and inspect ComponentIndex.md.
Confirm the target is not dirty and that no other agent owns the same file.
Implement one ticket, build the app, and launch the exact built artifact.
Capture the relevant surface in light and dark appearance when applicable.
Compare against the baseline; a build alone is not visual verification.

For every ticket, verify:

- Apple API candidate and coverage are recorded in the commit body.
- No custom color literal or new third-party dependency was introduced.
- No child chrome component accepts parent styling overrides.
- Existing callers and accessibility labels remain reachable.
- `git grep` finds no stale helper callers after a deletion.
- The working tree contains only the intended ticket before commit.

## 5. Ordering and risk

Recommended order is T2-05, T2-06, T2-07, T2-03, T2-04, T2-01, then T2-02.
The early tickets are narrow and establish the visual baseline. T2-01 and
T2-02 are later because they change composition and have the highest layout
blast radius. Roll back a ticket with git revert if the screenshot regresses.

Out of scope: domain persistence, editor behavior, library JSON topology,
new dependencies, and any Tier-3-only spelling or date modernization.

## 6. Definition of done

All named surfaces use the narrowest Apple API that covers their behavior.
The six zones preserve PaneTabBar behavior and symmetric parent-owned styling.
Screenshots show no unintended chrome duplication, pane transparency, or
selection loss. Each ticket has one English commit and an auditable diff.
